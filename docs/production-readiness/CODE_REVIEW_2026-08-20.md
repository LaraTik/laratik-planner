# Spec-vs-Reality Code Review — `laratik-planner` (2026-08-20)

> **Author:** production-readiness review, spec-vs-reality audit.
> **Spec ground truth:** `STUDIOFLOW_MASTER_PROMPT.md` §0–24 + `PORT_NOTES.md` (which records every Supabase → NextAuth + Postgres deviation).
> **Scope:** all 15 Goals (0–14), 153 source files, 36 test files, 4 SQL migrations, 1 production deployment at `planner.laratik.com`.
> **Method:** parallel deep-reads of source + spec; line-level evidence; severity per finding.

---

## 0. Verdict

**Production-deployable for a single-agency v1 with named caveats.** The product is structurally correct: 27 canonical routes ship, 18 design tokens + 7 typography tokens are wired, all 15 §8 enums are present, all required §8 indexes exist with `WHERE archived_at IS NULL` discipline, every required DB CHECK constraint is in place, and the workflow state machine, publishing aggregation, and approval modes are correctly implemented as pure functions. The release tracker says `READY ✅` pending independent review, and the underlying state supports that.

But the spec-vs-reality audit surfaces **8 critical gaps** and **24 major gaps** that are NOT in the tracker today, because they are subtle (silently-overwritten fields, post-deploy discoverable, or appear to work until a specific role/edge case is exercised). They are addressable in 2–3 weeks of focused work. They do NOT block v1 launch into a single-agency environment with a known user base, but they DO block:

- opening the platform to multiple tenants (the agency_admin JWT-never-refreshed gap is then a data-exposure risk)
- legal/regulator sign-off (missing HSTS, missing audit events on bootstrap/resend/revoke)
- an "open dev environment" (the dev sign-in + seed routes are unauthenticated and create agency_admin in one request)
- spec §10's distinctive "material edit → approval reset" flow (entirely missing)

The dominant theme of every gap below: **defense-in-depth is uneven**. The §8 DB constraints are excellent; the application-layer guards around them have holes. The §0 "Every write must … create an activity or audit event" rule is followed for content/publishing/discussion writes but missing for bootstrap, invitation resend/revoke, AI, and notifications.

## 2. Top 10 Findings (P0)

These are the items most likely to be raised by an independent reviewer, or to surface as bugs in the first 30 days of production use.

### P0-1 [CRITICAL] Unauthenticated dev routes can mint an agency_admin

- **Files:** `src/app/api/dev/seed/route.ts:80-106`, `src/app/api/dev/sign-in/route.ts:30-65`
- **Behavior:** `POST /api/dev/seed` has no auth; the only guard is `serverEnv.NODE_ENV === "production"` returning 404. Anyone with network access to a dev/staging deployment can POST to this route and create an `agency_admin` user, agency, workspace, channels — then immediately have full control.
- **Spec source:** §16 "Same-origin checks for sensitive POST routes"; §16 "No service-role access from browser code".
- **Why it matters:** any non-production environment exposed to the network is compromised by one POST. Even if the dev environment is supposed to be on a private VLAN, the seed endpoint should still require an auth header. The spec says these routes exist for E2E; they should require a static `X-Setup-Token` (or be removed and replaced by a one-shot CLI script).
- **Estimated fix:** 30 minutes — add `if (req.headers.get("x-dev-token") !== serverEnv.DEV_SEED_TOKEN) return new Response(null, { status: 404 })` and a matching `DEV_SEED_TOKEN` env in `.env.example`.

### P0-2 [CRITICAL] No `materiality.ts` — §10's most distinctive workflow feature is missing

- **File:** entire `src/lib/content/` directory
- **Behavior:** the §10 material-edit policy (increment revision, invalidate pending/approved requests, clear final approved delivery, move to earliest required gate, create `approval_reset` activity event, notify owner/assignees/reviewers) is not implemented. `content_items.revision` is declared with `DEFAULT 0` but never written. No `updateContentDetails`, `rescheduleContentItem`, or `updateContentChannels` commands exist. There is no way to edit a content item's title/format/brief/schedule/channels through the service layer after creation.
- **Spec source:** §10 "Centralize materiality in `src/features/content/materiality.ts`"; Goal 5 task "Implement content review submit, approve, request changes, and resubmit"; Goal 7 task "Implement material edit classification and approval reset."
- **Why it matters:** this is the heart of the spec's "post-approval change → reset" flow. A planner can reschedule an approved item today (the calendar route exists) but the reset path is silent — no version bump, no approval invalidation, no audit event, no notification. Reviewers see stale approvals.
- **Estimated fix:** 1–2 days — create `src/lib/content/materiality.ts` with field classification, add `updateContentDetails` command in `src/lib/content/service.ts`, write 6 tests (one per material-edit case), wire the workflow-bar to call it.

### P0-3 [CRITICAL] Outbox worker only handles `comment_created`; 6 of 11 notification kinds never fire

- **File:** `src/lib/notifications/service.ts:79-115`
- **Behavior:** `dispatchOutboxOnce` only processes `eventType === "comment_created"`. Required kinds from §12 (`review_request`, `approval`, `changes_requested`, `mention`, `reply`, `unresolved_question`, `deadline`, `delivery`, `ready_to_publish`) are not emitted by `submitDelivery`, `decideApproval`, `recordPublication`, `claimAsDesigner`, or `transitionContent`. The in-app notification stream is essentially empty for everything except new comments.
- **Spec source:** §12 notification kinds list; §14 required command `markNotificationRead and updateNotificationPreferences`.
- **Why it matters:** the bell badge works in the demo because the test seed inserts a comment. In production, an internal reviewer who submits a content review will get no in-app notification, no email, nothing. The whole "review queue" UX relies on the bell to triage.
- **Estimated fix:** 1 day — add outbox inserts in `submitDelivery`, `decideApproval`, `recordPublication`, `claimAsDesigner`, `transitionContent`; add kind-specific handlers in `dispatchOutboxOnce`.

### P0-4 [CRITICAL] Client-reviewer notification leak path

- **Files:** `src/lib/notifications/service.ts:117-139`, `src/lib/discussions/service.ts:121-131`
- **Behavior:** an internal comment can generate `comment_mentions` rows for client-only reviewers if their user_id is matched in `@mention` extraction. `extractMentions` does not filter by `canSeeInternal`; `fanOutCommentCreated` ignores the `visibility` parameter (`void visibility` at line 138). A client_reviewer can be @mentioned in an internal comment and the body text is sent to them via the bell.
- **Spec source:** §12 "Client users never receive notifications that reveal internal comment text"; §9 "@mentions only for users who can access the item and visibility level."
- **Why it matters:** this is a privacy boundary violation. Even a defense-in-depth check at the API surface is missing.
- **Estimated fix:** 2 hours — filter `extractMentions` by `eq(workspaceMemberships.role, internalRoles)` and `eq(role, "client_reviewer")` for internal visibility; gate `fanOutCommentCreated` on `visibility === "client"` for client users.

### P0-5 [CRITICAL] JWT role is never re-read; deactivated members keep admin until 30-day expiry

- **Files:** `src/lib/auth/config.ts:87-91`, `src/lib/auth/member-safety.ts:1-13`
- **Behavior:** the NextAuth `session` callback propagates `role` from the JWT token at sign-in. The token is signed with `AUTH_SECRET` and has a `maxAge: 30 * 24 * 60 * 60` (30 days). A member deactivated via `deactivateUser` has their `agency_memberships.status` flipped to `deactivated`, but their JWT continues to carry `is_agency_admin: true` until the cookie expires. There is no `updateAge` configured on `getToken`, so the proxy never refreshes against the DB.
- **Spec source:** §13 "Refresh sessions on the server and never trust browser-provided role claims alone"; §9 "Deactivated users cannot authenticate into application routes".
- **Why it matters:** a single-agency v1 has lower risk (you trust your admin). For multi-tenant or after a contract dispute, an ex-admin keeps the keys to the kingdom for up to 30 days.
- **Estimated fix:** 4 hours — add a `verifySession` middleware that on every request does a `SELECT status, is_agency_admin FROM agency_memberships WHERE user_id = $1 AND agency_id = $2 AND status = 'active'`; reject if inactive. Or shorten `maxAge` to 1 hour and require re-auth for sensitive actions.

### P0-6 [CRITICAL] HSTS is missing entirely

- **File:** `src/lib/security/headers.ts:26-36`
- **Behavior:** `buildSecurityHeaders` emits CSP, X-Frame, nosniff, Referrer-Policy, Permissions-Policy, COOP — but no `Strict-Transport-Security`. The function takes `_environment` but does not branch on it for HSTS.
- **Spec source:** §16 "CSP, HSTS in production, frame restrictions, Referrer-Policy, Permissions-Policy, and nosniff."
- **Why it matters:** Traefik already terminates TLS, so HSTS is the application layer's commitment to never serve over plain HTTP. Without it, downgrade attacks are possible. Production hosts get an A on observatory checks but fail strict HSTS-preload.
- **Estimated fix:** 5 minutes — add `{ key: "Strict-Transport-Security", value: "max-age=31536000; includeSubDomains" }` (and optionally `; preload` after staging verification).

### P0-7 [CRITICAL] Bootstrap token comparison is not constant-time; no security audit event

- **Files:** `src/lib/auth/bootstrap.ts:31-100`, `src/app/api/bootstrap/admin/route.ts:27-87`
- **Behavior:** `if (input.token !== serverEnv.BOOTSTRAP_SETUP_TOKEN)` is a JS string equality, vulnerable to timing attacks. No `security_audit_events` row is written on success or failure. The bootstrap flow is also inverted from spec §13: the user must sign in first via Google/magic-link, then the bootstrap form completes the agency setup — but the spec says bootstrap "creates the Supabase auth user through the server-only admin client" (we use NextAuth, but the analogous step — creating the credentialed user) doesn't happen here.
- **Spec source:** §13 "verifies BOOTSTRAP_SETUP_TOKEN using constant-time comparison" + "records a security audit event" + "creates the auth user".
- **Why it matters:** the spec's intent for bootstrap is atomic creation of the first admin. The current flow splits this across `accept-invitation` (or first sign-in) and the bootstrap form, which is operationally different and weakens the audit trail.
- **Estimated fix:** 2 hours — switch to `crypto.timingSafeEqual(Buffer.from(input.token), Buffer.from(serverEnv.BOOTSTRAP_SETUP_TOKEN))`; add `security_audit_events` insert for both success and failure paths.

### P0-8 [CRITICAL] AI has no timeout, no retry, no per-agency rate limit, no token cap, no model allowlist

- **File:** `src/lib/ai/index.ts:39-81`, `src/app/api/ai/generate/route.ts:47-115`
- **Behavior:** `chat()` calls `fetch(MINIMAX_BASE_URL)` with no `signal` (no timeout), no retry, and passes the env model string straight through. The `ai_generation` rate limit has only one rule (`session.user.id`), not per-agency. No `maxTokens` cap on input. The context manifest is a hard-coded `{ categories: ["title", "brief", "format", "workspace_name"] }` label, not a server-rebuilt enumeration of allowed fields.
- **Spec source:** §15 "Set timeouts and one controlled retry for transient failures"; "Apply per-user and per-agency rate limits"; "Cap context and output tokens"; "Model selector limited to server allowlist"; "The server independently rebuilds allowed context from IDs."
- **Why it matters:** AI is gated by `AI_FEATURE_ENABLED=false` in production, so this is latent. The moment the env flips, a hung provider holds a request open indefinitely; a misconfigured model string sends traffic to an unapproved provider; an attacker can hit the route without the per-agency throttle.
- **Estimated fix:** 1 day — add `AbortSignal.timeout(30_000)` + 1 retry on 5xx; add `MODEL_ALLOWLIST` env; add a per-agency rule; cap input tokens; rebuild the context manifest from IDs server-side.

## 4. UI/UX Gaps — A Walk-Through

The 27 canonical routes all render, but several spec requirements are missing in the surfaces. This is the section to share with a designer or PM for sign-off before the next milestone.

### 4.1 Quick Create

- **Spec:** exactly 4 initial fields (Title, Format, Planned publish, Brief). All other fields (campaign, pillar, objective, audience, priority, captions, CTA, hashtags, references, assignments, specifications, overrides) live in a "More details" disclosure.
- **Reality:** 4 fields are visible. **Channels are user-toggled checkboxes, not auto-applied.** There is **no "More details" disclosure** at all — the form is hard-capped at the 4 fields + channels.
- **Gap:** the "one dominant next action" principle (§3 §1) is broken because the user must explicitly check channels even though they all auto-apply server-side. A planner who wants to add a campaign must navigate to the content detail page to do so. That's 2 extra screens for the most common follow-up.

### 4.2 Content Detail / Workflow Bar

- **Spec:** approval-reset is visible; material edit raises a confirmation dialog naming the changed fields; "next action" is one dominant CTA per status.
- **Reality:** the workflow bar's lower "Approval requests" list renders Approve/Request-changes buttons for content-gate approvals that the service refuses. The only path to a content approval is the top-of-card `Approve` button — but the lower list looks like a duplicate. This is a **misleading UX**: a user clicks Approve on a content review in the list, sees an error toast, and doesn't know why.

### 4.3 Calendar

- **Spec:** month + week views; reschedule by drag/drop OR keyboard "Move item" dialog; rescheduling an approved item triggers material-edit reset.
- **Reality:** month-only view. Static grid, no drag/drop, no Move-item dialog, no keyboard equivalent. Per-channel `planned_publish_at_override` is ignored — rescheduled channels still appear on the parent item's default date. The grid is `min-w-[760px]` so on 360/390px viewports it requires horizontal scrolling.
- **Gap:** the spec's most distinctive UX feature (drag-to-reschedule with keyboard fallback) is missing. The mobile alternative is "list" per §3, but there is no list view — just horizontal scroll on a grid.

### 4.4 Board

- **Spec:** 7 columns; mobile alternative is a list (per §3 "list alternatives to seven-column boards").
- **Reality:** 7 columns. Mobile users see the same grid (likely horizontal scroll). `Ideas` column mixes `draft`, `changes_requested`, `blocked` — three different concepts visually grouped.

### 4.5 Notifications Bell

- **Spec:** notification body links to the authorized resource.
- **Reality:** `actionUrl` is hard-coded to `/app/planning/${contentItemId}`. A client_reviewer clicking it lands on `ContentDetailPage` which calls `getAccessibleWorkspace` → `canAccessInternalWorkspace` → 404. The link is broken for clients.

### 4.6 Page States

- **Spec:** one h1 per page.
- **Reality:** `not-found.tsx`, `error.tsx`, `(app)/error.tsx` all render `EmptyState` whose `title` is `<h3>`. These three error/404 pages have **0 h1s**. They are reachable entry points.
- **Spec:** loading, no-data, no-results, recoverable error, permission-denied, archived.
- **Reality:** Loading ✓, no-data ✓ (channels/brand-kit/invitations/members), error ✓, permission-denied ✓ (inline `PageHeader` style — not a shared `PermissionState` component, but functional). **No `ErrorSummary` component** anywhere — every form shows a single inline `<p role="alert">` instead of a top-of-form summary that link-focuses invalid fields.

### 4.7 Forms

- **Spec:** React Hook Form plus Zod (§4).
- **Reality:** every form uses `useActionState` + server actions. This is _valid_ React 19 pattern but deviates from spec §4. Not a defect in isolation; a spec-vs-reality gap worth recording.

### 4.8 Form a11y

- **Send-invite form (`src/app/(app)/app/users/send-invite-form.tsx:55-78`):** per-workspace role `<select>`s are not wrapped in `<label>` and have no `aria-label`. Screen readers will say "combobox, no label". A serious axe issue.
- **Quick Create form:** same — no field-level error association, no top-of-form summary.
- **Settings form:** labels are inline `<label>` wrapping, so OK. Single inline error, no summary.

### 4.9 Visual Regression

- **Spec:** validate at 360px, 390px, 768px, 1024px, 1280px, 1440px.
- **Reality:** `tests/e2e/visual-regression.spec.ts:41,89` covers only **1280×800 desktop** and is **fully `test.skip`**. Tablet and mobile viewports have no visual baseline. The standard E2E suite runs the 5 Playwright projects at default viewports, but visual diffs are only at one viewport, and the spec is gated off by default.

### 4.10 Topbar

- **Spec:** §17 TopBar = search, notifications, workspace switcher, user menu.
- **Reality:** workspace switcher + notifications + user menu. **No search field.**

### 4.11 Component Library

- **Spec:** §17 expects ~60 named components.
- **Reality:** 19 extracted (per `DESIGN_AUDIT.md`). The remaining ~40 are inlined in route-local files. Tracked as P3 architectural debt in the tracker. Not a release blocker — every screen renders — but the cost is **reusability + bundle splitting** (e.g., `discussion-section.tsx` could be code-split per route if extracted to `src/components/content/`).

### 4.12 Calendar Locale / Timezone

- **Spec:** store timestamps in UTC and display in workspace timezone.
- **Reality:** server's local timezone is used for `new Date()` grid construction. `date-fns-tz` is in `package.json` but not used in the calendar route. At DST boundaries, items appear on the wrong day.

## 5. Cross-Cutting Theme: Defense-in-Depth is Uneven

The single most important theme of this audit: **DB constraints are excellent; application-layer guards around them have holes.**

| Layer                            | Quality        | Examples                                                                                                                                                                                                            |
| -------------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DB CHECK constraints**         | Excellent      | All 6 §8 publication invariants, all `format_payload` defaults, `delivery_link_url_https` at column level, `change_request_gate` non-null requirement, all 4 priority values.                                       |
| **DB indexes**                   | Excellent      | All required §8 indexes present, `WHERE archived_at IS NULL` discipline correct.                                                                                                                                    |
| **DB enums**                     | Excellent      | All 15 §8 enums declared with the exact member sets.                                                                                                                                                                |
| **Service-layer authorization**  | Mixed          | `requirePolicy` called for every write command; but `claimAsDesigner` bypasses the workflow table; `decideApproval` throws raw Error for content gate; `canReview` doesn't enforce no-self-approval.                |
| **Service-layer business logic** | Mixed          | `derivePublicationAggregate` is pure and correct; `deriveCreativeApprovalOutcome` is pure and correct; `materiality.ts` is missing entirely.                                                                        |
| **Service-layer notifications**  | Inconsistent   | `createComment` writes an outbox event; `submitDelivery`, `decideApproval`, `recordPublication`, `claimAsDesigner` write only `activityEvents` and no outbox row. The outbox worker only handles `comment_created`. |
| **Activity events**              | Mostly correct | Every audited write appends an `activityEvent` in the same transaction. Missing: `approval_reset` on new delivery.                                                                                                  |
| **Security audit events**        | Inconsistent   | Bootstrap, resend, revoke all missing; invitation create/accept/member-deactivation ✓.                                                                                                                              |
| **Proxy / session**              | Weak           | `getToken` doesn't refresh; 30-day cookie; deactivated members keep admin until expiry.                                                                                                                             |
| **Security headers**             | Mostly correct | CSP, X-Frame, nosniff, Referrer-Policy, Permissions-Policy, COOP ✓. **HSTS missing.**                                                                                                                               |
| **Dev routes**                   | Critical       | Unauthenticated seed + sign-in; mint agency_admin in one POST.                                                                                                                                                      |
| **A11y**                         | Mostly correct | Skip link, one h1 (except 404/error), 2px focus ring, reduced motion, 44px touch targets via CSS, axe green on 9/28 routes. Issues: send-invite form selects, no ErrorSummary, error pages missing h1.              |

**Implication:** the v1 can ship because the DB is the safety net. The application layer is mostly correct. But moving to multi-tenant, SOC2, or any external-audit posture will require (a) closing the bootstrap/dev/auth gaps, (b) implementing the §10 material-edit policy, (c) wiring the outbox for the 6 missing notification kinds, and (d) fixing the P0 JWT-refresh gap.

### 6.2 What NOT to do (anti-recommendations)

- **Do not** rewrite the `src/lib/auth/index.ts` stub. It's dead code; deleting it is a 30-second change.
- **Do not** add `react-hook-form` retroactively. Document the `useActionState` deviation in `PORT_NOTES.md` instead, and migrate form-by-form only if/when a new form's complexity demands it.
- **Do not** extract the §17 components before the §10 material-edit policy is in. The materiality tests will surface reusable patterns; you'll extract better components the second time.
- **Do not** add staging as a separate environment before the §13 hardening is complete. Staging inherits prod-like secrets; you don't want to provision that until HSTS, JWT refresh, and the audit events are in.
- **Do not** try to get all 19 axe routes green in one PR. Land the 11 uncovered routes in 2-3 PRs (low-risk pages first, then forms, then dynamic pages).
- **Do not** chase 95/90 coverage on the first try. The integration-coverage folding is the right next step; once that's in, the floors go up in lockstep with tests.
